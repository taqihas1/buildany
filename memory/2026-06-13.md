## BuildAny Orchestrator Architecture Issue (Confirmed - June 13, 2026)

### Finding: Orchestrator Still Bypasses Agents
After reading `src/lib/orchestrator.ts` in `/root/buildany`, confirmed the orchestrator (`HermesOrchestrator`) still handles ALL execution directly:

- `decomposeAndAssignTasks()` creates DB task records and sets agents to `busy`
- BUT `executeCodeAgent()` directly calls `llmRouter.generate()` with `provider: 'deepseek'`, `temperature: 0.7`, `maxTokens: 4000`
- The assigned DB agents/tasks are NEVER used for actual execution
- Agents and tasks exist purely for dashboard display/tracking

### File Location
- `/root/buildany/src/lib/orchestrator.ts` — `HermesOrchestrator` class
- Methods: `decomposeAndAssignTasks()`, `executePhase()`, `executeCodeAgent()`

### This Means
- Tasks created by UI ("Create project tasks" button) → stored in DB with status `pending`/`ready`
- Orchestrator ignores those tasks and generates code directly via LLM
- Task statuses are updated post-hoc (set to `working`/`completed` after orchestrator finishes)
- Agents are decorative — they don't actually execute anything

### User's Stated Preference
User explicitly wants:
1. Wiki/Design FIRST (documented in wiki pages)
2. Code generation based on design (not blind)
3. Code Review step
4. Preview/Test step
5. Iteration loop
6. CI/CD only after user confirms

The current architecture does NOT support this workflow. The orchestrator needs significant refactoring to:
- Read tasks from DB (created by UI decompose API)
- Execute each task step-by-step following the user's desired workflow
- Use agents meaningfully (each agent type handles its assigned task type)
- Generate wiki pages first, then code, then review, then preview


## BuildAny Orchestrator Fix — June 13, 2026 (Night)

### Decision: Bypass Agents/Tasks for This Release
User confirmed: "bypass this agents and tasks flows, so orchestrator does everything create wiki pages, generate code, review code, generate preview. The agents and tasks workflow we would work in next release in future."

### Changes Made to `src/lib/orchestrator.ts`

1. **Task creation for display only** — `decomposeAndAssignTasks()` creates tasks in DB for visual progress tracking, but explicitly comments that "agents are decorative in this release"
2. **Orchestrator handles all execution** — `start()` method runs: `decomposeAndAssignTasks()` → `generateWikiPages()` → `executeCodeAgent()` → `executeTestAgent()` → `executeReviewAgent()` → `executePreviewAgent()` → `markAllTasksCompleted()`
3. **Flexible task status matching** — `updateTaskStatus()` now uses keyword matching instead of exact title matching, so tasks get updated regardless of title variations
4. **Task titles aligned with decompose API** — `decomposeProject()` uses same task names as `/api/decompose` endpoint: "Research & Pattern Analysis", "Architecture & File Structure", "Page Components", "API Routes & Backend", "Pre-flight Validation", "Visual Assets & UI Polish", "Code Review & Quality Check", "CI/CD Pipeline"
5. **Wiki pages generated first** — `generateWikiPages()` runs before code generation, updates research task status to `completed`
6. **All tasks marked completed at end** — `markAllTasksCompleted()` sets all tasks to `completed` and all agents to `idle` when orchestrator finishes

### Current Flow
1. User creates project → orchestrator starts
2. Orchestrator creates display tasks (for UI progress tracking)
3. Orchestrator generates wiki pages from research
4. Orchestrator generates code directly via LLM
5. Orchestrator runs basic tests
6. Orchestrator runs code review
7. Orchestrator generates preview
8. Orchestrator marks all display tasks as completed
9. Project status set to `completed`

### What Still Needs Work for Next Release
- True multi-agent workflow where each agent type executes its assigned tasks
- Task dependency resolution (tasks waiting for dependencies before starting)
- Agent-specific execution logic (different code for code agent vs test agent vs review agent)
- Parallel task execution across multiple agents
- User approval gates between phases (Design → Approve → Build → Approve → etc.)
